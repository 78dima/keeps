# MonoKeep — Android

Android-приложение на Flutter с локальной SQLite. Исходная версия для сравнения находится в `../web`. WebView, сервер, аккаунт и соединение с интернетом для работы приложения не нужны. Release-манифест не запрашивает `INTERNET`.

## Что перенесено

Повторный импорт с тем же ID или тем же JSON не перезаписывает локальные изменения. Импорт новых записей выполняется в одной транзакции. Ошибки отдельных файлов показываются пользователю. Максимальный объём одного выбора файлов — 32 MiB; большой Takeout можно импортировать частями. ZIP, изображения, аудио и совместный доступ не поддерживались исходным редактором и здесь не добавлены.

Веб-приложение смешивает английские и русские надписи — этот вариант сохранён. Визуальное совпадение требует сверки скриншотов на реальном Android/эмуляторе; CSS и Flutter могут отличаться в растеризации и переносах текста.

## Сборка APK

На Linux x86_64 с интернетом и Python 3.12+:

```bash
cd apps/android
python3 tools/bootstrap_linux.py
./tools/build_apk.sh
```

`bootstrap_linux.py` загружает Flutter 3.32.8, Temurin JDK 17 и Android SDK 35 в локальный каталог `.toolchain/`, принимает лицензии пакетов Android SDK. Он не меняет системные пакеты и shell-конфигурацию. Для Flutter и JDK проверяются SHA-256 из метаданных поставщиков. Также нужны стандартные системные `git`, `unzip`, `xz` и библиотеки Linux, указанные в документации Flutter.

Если инструменты уже установлены, достаточно настроить `PATH`, `JAVA_HOME`, `ANDROID_HOME` и запустить `./tools/build_apk.sh`. SDK должен содержать API 35, Build Tools 35.0.0 и NDK 27.0.12077973.

Сценарий скачивает закреплённые ревизии исходных шрифтов с OFL-лицензиями и Gradle wrapper 8.11.1, выполняет `flutter analyze`, `flutter test`, собирает release APK и проверяет его подпись. Результат:

```text
apps/android/dist/monokeep-release.apk
apps/android/dist/monokeep-release.apk.sha256
```

Один APK содержит Android ABI arm64-v8a, armeabi-v7a и x86_64. Минимальная версия — Android 6 (API 23); target/compile SDK — 35.

При первой локальной сборке создаётся постоянный ключ `.toolchain/monokeep-release.jks`, настройки — `android/key.properties`. Они исключены из Git. Сохраните оба файла отдельно: обновление установленного APK с сохранением заметок требует того же ключа и увеличенного build number в `pubspec.yaml`. Удаление приложения удаляет локальные заметки; резервные копии доступны через Export backup. Автоматическое облачное резервное копирование отключено.

Установка:

```bash
adb install -r dist/monokeep-release.apk
```

В репозитории есть workflow `.github/workflows/android.yml`. Push в ветку `codex/android-apk` автоматически запускает облачную сборку тестового debug APK. Локально Flutter и Android SDK для этого не нужны. После входа в GitHub CLI запустите из подготовленной ветки:

```bash
./tools/cloud_apk.sh
```

Сценарий отправляет ветку, ждёт завершения GitHub Actions и скачивает APK в `dist/cloud-RUN_ID/`, проверяя SHA-256. При ошибке сборки выводится лог. Debug APK предназначен для проверки приложения; это не release-сборка с постоянным ключом.

Также доступен ручной запуск workflow. Режим `release` требует secrets `MONOKEEP_KEYSTORE_BASE64` и `MONOKEEP_KEY_PROPERTIES_BASE64` — Base64 содержимого двух файлов от локальной сборки.

## Android-интеграция

`lib/platform/native_store.dart` общается с Java через Flutter MethodChannel. SQLite находится в приватной директории приложения (`databases/monokeep.db`), работает с WAL. `NoteDatabase` и все получатели событий используют один последовательный исполнитель; запись статуса напоминания не перезаписывает дату изменения заметки.

Напоминания используют абсолютное время в миллисекундах UTC. Системные DatePicker/TimePicker работают в локальном часовом поясе. Разрешение `POST_NOTIFICATIONS` запрашивается при выборе первого напоминания. Для точных сигналов на Android 12+ предусмотрен переход к `SCHEDULE_EXACT_ALARM`; если доступ не предоставлен, используется неточное расписание и интерфейс сообщает об этом. Заблокированное уведомление не помечается отправленным.

Нажатие на уведомление открывает нужную заметку при холодном и повторном запуске. `BOOT_COMPLETED`, обновление приложения, изменение часов/часового пояса и выдача доступа к точным сигналам восстанавливают расписание. Принудительная остановка в системных настройках Android блокирует фоновую работу до следующего открытия приложения. Обычное закрытие интерфейса не требует работающего Flutter-процесса.

Системные API и правила разрешений: [Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels), [Android alarms](https://developer.android.com/develop/background-work/services/alarms), [notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission), [AGP 8.9 compatibility](https://developer.android.com/build/releases/agp-8-9-0-release-notes).

## Проверки

```bash
# Доступно без Flutter: схема SQLite, соответствие канала, манифесты и иконки.
python3 tools/test_schema.py

# После подготовки шрифтов и SDK:
python3 tools/prepare.py
flutter pub get
flutter analyze

# На отдельном тестовом Android-устройстве/эмуляторе:
flutter test integration_test/app_test.dart -d DEVICE_ID

```

Тесты Dart покрывают сортировку, поиск, импорт/экспорт, UI-сценарии, ошибки сохранения и ширины 320/640/800/1280. Android instrumentation проверяет реальный SQLite, повторное открытие, откат импорта, защиту от устаревшего редактора, повторную постановку напоминания и идентичность PendingIntent.

Перед выпуском на устройстве проверить: уведомление с закрытым интерфейсом; нажатие на уведомление при закрытом/открытом приложении; перезагрузку; запрет уведомлений и точных сигналов; смену времени; удаление/восстановление напоминания; выбор файлов и экспорт; поворот экрана и клавиатуру; масштаб шрифта; обновление APK с сохранением базы.

## Статус в исходной рабочей среде

Flutter, Dart, JDK, Android SDK и эмулятор в среде отсутствуют; сетевые загрузки из терминала недоступны (`Could not resolve host: storage.googleapis.com`). Поэтому APK, выполнение Flutter/Android-тестов и сравнение скриншотов здесь пока не получены. Проверки без SDK отдельно записываются в `VALIDATION.md`; их успех не означает успешную компиляцию приложения.

## Синхронизация с веб-версией (v1.1)

В меню «Синхронизация и аккаунт» войдите с email и паролем того же аккаунта Supabase, что используется в вебе. Существующие локальные заметки привязываются к первому выбранному аккаунту; данные другого аккаунта никогда не перепривязываются. После выхода его заметки и очередь остаются в SQLite и снова доступны после входа.

Каждая правка атомарно сохраняет заметку и снимок для отправки. Сравниваются исходное время редактирования и UUID правки, а не время загрузки. Конфликт разрешается для всей заметки целиком, без объединения абзацев. Проигравшие серверные версии доступны владельцу в `note_conflicts`. Удаления передаются как версии с `sync_deleted`; старая копия не отменяет более новое удаление. Правка, реально выполненная позднее удаления на другом офлайн-устройстве, может победить по тому же правилу.

В открытом приложении работают Supabase Realtime и немедленная синхронизация. Android WorkManager повторяет отправку при доступной сети, дополнительно проверяя сервер примерно раз в 15 минут или позднее по решению Android. FCM сообщает лишь «есть изменения» без текста заметок и уведомлений на экране. Отправитель проверяет накопленную очередь раз в минуту; доставка FCM также зависит от энергосбережения. При открытии всегда выполняется проверка обновлений. Принудительная остановка приложения и ограничения Android могут отложить фоновую работу.

Напоминания планируются локальным AlarmManager. Отправка веб-пуша не подавляет напоминание телефона; факт доставки не меняет время пользовательской правки. Сессия Supabase шифруется ключом Android Keystore, пароль не сохраняется. В `sync-config.json` находится только публичный ключ проекта; привилегированных ключей в APK нет.

Для времени применяется поправка по часам сервера. Абсолютный порядок двух офлайн-правок при неверных часах обоих устройств установить невозможно. Сервер отклоняет правки более чем на пять минут из будущего, сохраняя их в локальной очереди; после исправления часов и синхронизации можно повторно сохранить такую заметку.

### Подготовка сервера и порядок выпуска

До применения SQL новый APK остаётся пригодным для локального использования, но синхронизация будет показывать ошибку. Рабочая база и веб-сервер обновляются только после отдельного согласования владельца.

1. Создать резервную копию серверной базы и сохранить текущую версию развёрнутого веб-приложения.
2. Применить `supabase/sync-v2.sql` как транзакционную миграцию. Она сохраняет исходные даты и данные, добавляет очереди, версионирование и RPC. Старые клиенты с `upsert` также подчиняются проверке времени.
3. Обновить веб-версию из той же проверенной ревизии. RxDB выполняет миграцию схемы без удаления локальных заметок и начинает полную проверку серверных данных. Старые открытые вкладки следует перезагрузить.
4. Установить APK, войти в тот же аккаунт, проверить редактирование в обе стороны, офлайн-конфликт и удаление.
5. Для FCM создать Firebase Android app `com.monokeep.app`; клиентские Firebase options передать в `android/app/src/main/assets/firebase-config.json` (applicationId, apiKey, projectId, senderId). JSON сервисного аккаунта с правом отправки FCM хранить только в Supabase Vault как `monokeep_firebase_service_account`; отдельный случайный секрет — как `monokeep_sync_dispatch_secret`. Развернуть `sync-dispatch` с собственной проверкой `X-Sync-Secret`, затем применить `supabase/sync-fcm.sql`. Секреты не отправлять в чат и не коммитить.

### Обновление уже установленного debug APK

Старый workflow не сохранял приватный ключ debug-подписи между облачными сборками. Если Android сообщает о несовместимой подписи, **сначала экспортируйте заметки через «Export backup» в старом приложении и проверьте JSON-файл**. Только имея резервную копию, можно выполнить однократную переустановку и импорт. Новые проверочные сборки используют общий ключ из GitHub Actions cache; потеря/очистка cache снова потребует переноса. Для постоянных выпусков используйте release APK и сохранённый приватный ключ из описанного выше механизма repository secrets.

### Проверки протокола

- `node --experimental-strip-types --test apps/web/tests/sync-protocol.test.mjs` — порядок правок, повторная доставка, удаление, часы.
- `python3 apps/android/tools/test_schema.py` — SQLite и Android platform wiring.
- `cd apps/android/android && ./gradlew connectedDebugAndroidTest` — реальная миграция SQLite v1→v2, ACK после новой правки, откат страницы, смена аккаунта и напоминания.
- `supabase/tests/before-migration.sql`, `supabase/sync-v2.sql`, `supabase/tests/after-migration.sql`, `supabase/tests/sync-v2.sql` выполняются последовательно в одной тестовой транзакции с `ROLLBACK`. Они не предназначены для применения как миграции в production.
