# MonoKeep — Android

Android-приложение на Flutter с локальной SQLite. Исходная версия для сравнения находится в `../web`. Локальные заметки и напоминания работают без аккаунта и интернета. Для синхронизации с веб-версией предусмотрен вход в Supabase; манифест содержит разрешения `INTERNET` и `ACCESS_NETWORK_STATE`. Состояние сборки и развёртывания описано в [VALIDATION.md](VALIDATION.md).

При создании можно сразу выбрать один из 12 цветов и напоминание через системные окна даты и времени Android. Эти значения сохраняются вместе с текстом и тегами. Close сбрасывает черновик; ошибка сохранения оставляет его открытым. Заголовки карточек показываются целиком. Регистрация и Telegram не входят в согласованный объём Android-приложения.

Повторный импорт с тем же ID или тем же JSON не перезаписывает локальные изменения. Импорт новых записей выполняется в одной транзакции. Ошибки отдельных файлов показываются пользователю. Максимальный объём одного выбора файлов — 32 MiB; большой Takeout можно импортировать частями. ZIP, изображения, аудио и совместный доступ не поддерживались исходным редактором и здесь не добавлены.

Веб-приложение смешивает английские и русские надписи — этот вариант сохранён. Визуальное совпадение требует сверки скриншотов на реальном Android/эмуляторе; CSS и Flutter могут отличаться в растеризации и переносах текста.

## Сборка APK

На Linux x86_64 с интернетом и Python 3.12+:

```bash
cd apps/android
python3 tools/bootstrap_linux.py
./tools/build_apk.sh
```

`bootstrap_linux.py` загружает Flutter 3.32.8, Temurin JDK 17 и Android SDK 35 в локальный каталог `.toolchain/`, принимает лицензии пакетов Android SDK. Он не меняет системные пакеты и shell-конфигурацию. Для Flutter и JDK проверяются SHA-256 из метаданных поставщиков. Также нужны стандартные системные `git`, `unzip`, `xz` и библиотеки Linux, указанные в документации Flutter.

Если инструменты уже установлены, достаточно настроить `PATH`, `JAVA_HOME`, `ANDROID_HOME` и запустить `./tools/build_apk.sh`. SDK должен содержать API 35, Build Tools 35.0.0 и NDK 27.0.12077973.

Сценарий скачивает закреплённые ревизии исходных шрифтов с OFL-лицензиями и Gradle wrapper 8.11.1, выполняет `flutter analyze`, `flutter test`, собирает release APK и проверяет его подпись. Результат:

```text
apps/android/dist/monokeep-release.apk
apps/android/dist/monokeep-release.apk.sha256
```

Один APK содержит Android ABI arm64-v8a, armeabi-v7a и x86_64. Минимальная версия — Android 6 (API 23); target/compile SDK — 35.

Для этого приложения уже создан постоянный release-ключ `.toolchain/monokeep-release.jks` (контейнер PKCS12), настройки — `android/key.properties`. Они исключены из Git. На чистом clone нужно восстановить эти файлы или использовать облачную сборку; скрипт не создаёт замену ключу. Закрытая резервная копия: `.secrets/android-release-signing/signing-backup.tar.gz` от корня репозитория. Сохраните архив отдельно: обновление установленного APK с сохранением заметок требует того же ключа и увеличенного build number в `pubspec.yaml`. Удаление приложения удаляет локальные заметки; резервные копии доступны через Export backup. Автоматическое облачное резервное копирование отключено.

Установка:

```bash
adb install -r dist/monokeep-release.apk
```

В репозитории есть workflow `.github/workflows/android.yml`. Push изменений приложения в ветку `codex/android-apk` автоматически запускает облачную сборку **release APK** с постоянной подписью. Локально Flutter и Android SDK для этого не нужны. После входа в GitHub CLI запустите из подготовленной ветки:

```bash
./tools/cloud_apk.sh
```

Сценарий отправляет ветку, ждёт завершения GitHub Actions и скачивает APK в `dist/cloud-RUN_ID/`, проверяя SHA-256. При ошибке сборки выводится лог. Для обычного использования предназначен `monokeep-release.apk`. Проверка сборки сверяет постоянный сертификат и запрещает debuggable-флаг; debug остаётся отдельным ручным режимом для диагностики.

Также доступен ручной запуск workflow; по умолчанию выбран `release`. Secrets `MONOKEEP_KEYSTORE_BASE64` и `MONOKEEP_KEY_PROPERTIES_BASE64` уже настроены. В Git хранится только публичный отпечаток `release-certificate.sha256`; он также зарегистрирован в Firebase.

## Android-интеграция

`lib/platform/native_store.dart` общается с Java через Flutter MethodChannel. SQLite находится в приватной директории приложения (`databases/monokeep.db`), работает с WAL. `NoteDatabase` и все получатели событий используют один последовательный исполнитель; запись статуса напоминания не перезаписывает дату изменения заметки.

Напоминания используют абсолютное время в миллисекундах UTC. Системные DatePicker/TimePicker работают в локальном часовом поясе. Разрешение `POST_NOTIFICATIONS` запрашивается при выборе первого напоминания. Для точных сигналов на Android 12+ предусмотрен переход к `SCHEDULE_EXACT_ALARM`; если доступ не предоставлен, используется неточное расписание и интерфейс сообщает об этом. Заблокированное уведомление не помечается отправленным и не воспроизводится позднее при выдаче разрешения.

Нажатие на уведомление открывает нужную заметку при холодном и повторном запуске. `BOOT_COMPLETED`, обновление приложения, изменение часов/часового пояса и выдача доступа к точным сигналам восстанавливают расписание. Принудительная остановка в системных настройках Android блокирует фоновую работу до следующего открытия приложения. Обычное закрытие интерфейса не требует работающего Flutter-процесса.

Системные API и правила разрешений: [Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels), [Android alarms](https://developer.android.com/develop/background-work/services/alarms), [notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission), [AGP 8.9 compatibility](https://developer.android.com/build/releases/agp-8-9-0-release-notes).

## Статус сборки

Для обычного использования подготовлен **release 1.1.6+12**: [скачать APK с сайта](https://monokeep.cloudpub.ru/download/android), [APK в GitHub](https://github.com/78dima/keeps/actions/runs/40675908150/artifacts/12810517711), [сборка и проверки](https://github.com/78dima/keeps/actions/runs/40675908150). При выключенных уведомлениях Android теперь показывает отправку напоминания из веба/Telegram; SQLite v5 хранит серверную отметку отправки и один раз заново загружает заметки после обновления. Включает ускорение большого списка из 1.1.5. Прошли 33 Flutter-теста; на Android — 39 instrumentation-тестов, 2 интеграционных сценария и запуск готового release на Android 15, crash log пуст. APK устанавливается поверх предыдущего release без удаления приложения. Подробности — в [VALIDATION.md](VALIDATION.md).

Серверная миграция, новая веб-версия и отправитель FCM развёрнуты 2026-10-27 после согласования владельца. Войдите в APK тем же аккаунтом Supabase; при первом входе заметки скачиваются в SQLite. Старые вкладки веб-приложения следует перезагрузить. Фактические результаты, путь к резервной копии и порядок отката находятся в [DEPLOYMENT.md](DEPLOYMENT.md).

## Синхронизация с веб-версией (v1.1)

В меню «Синхронизация и аккаунт» войдите с email и паролем того же аккаунта Supabase, что используется в вебе. Существующие локальные заметки привязываются к первому выбранному аккаунту; данные другого аккаунта никогда не перепривязываются. После выхода его заметки и очередь остаются в SQLite и снова доступны после входа.

Каждая правка атомарно сохраняет заметку и снимок для отправки. Сравниваются исходное время редактирования и UUID правки, а не время загрузки. Конфликт разрешается для всей заметки целиком, без объединения абзацев. Проигравшие серверные версии доступны владельцу в `note_conflicts`. Удаления передаются как версии с `sync_deleted`; старая копия не отменяет более новое удаление. Правка, реально выполненная позднее удаления на другом офлайн-устройстве, может победить по тому же правилу.

В открытом приложении работают Supabase Realtime и немедленная синхронизация. Android WorkManager повторяет отправку при доступной сети, дополнительно проверяя сервер примерно раз в 15 минут или позднее по решению Android. FCM сообщает лишь «есть изменения» без текста заметок и уведомлений на экране. Отправитель проверяет накопленную очередь раз в минуту; доставка FCM также зависит от энергосбережения. При открытии всегда выполняется проверка обновлений. Принудительная остановка приложения и ограничения Android могут отложить фоновую работу.

Напоминания планируются локальным AlarmManager только на будущую дату, если они включены и ещё не отправлены. Загрузка истории, открытие приложения, перезагрузка и повторный вход не показывают просроченные уведомления. SQLite v4 хранит локальную отметку постановки конкретной версии напоминания: только системный AlarmReceiver может доставить ранее запланированный сигнал с задержкой. Одновременная веб-доставка не отменяет такой действующий сигнал телефона. При загрузке старых записей учитывается серверный факт отправки; отметка постановки не переносится из облака или резервной копии и сбрасывается при смене версии/даты и входе/выходе. Факт доставки не меняет время пользовательской правки. Сессия Supabase шифруется ключом Android Keystore, пароль не сохраняется. В `sync-config.json` находится только публичный ключ проекта; привилегированных ключей в APK нет.

Для времени применяется поправка по часам сервера. Абсолютный порядок двух офлайн-правок при неверных часах обоих устройств установить невозможно. Сервер отклоняет правки более чем на пять минут из будущего, сохраняя их в локальной очереди; после исправления часов и синхронизации можно повторно сохранить такую заметку.

### Подготовка сервера и порядок выпуска

SQL и веб-версия уже обновлены с разрешения владельца. Для других установок сначала нужен совместимый серверный протокол; порядок описан ниже.

Подробный порядок приведён в [DEPLOYMENT.md](DEPLOYMENT.md). В общих чертах: резервные копии → транзакционная SQL-миграция → совместимый отправитель напоминаний и готовый веб-пакет → Vault/FCM → проверка APK и браузера. Старая открытая вкладка без версии правки получит явную ошибку и требует перезагрузки.

Веб сохраняет базу `monokeepdb_v5` и перед миграцией создаёт точную локальную копию прежних заметок. Она доступна через «Копия заметок до обновления». Старый веб не всегда менял время при редактировании текста, поэтому порядок таких старых офлайн-черновиков восстановить автоматически нельзя; копия позволяет вернуть их вручную. Новые правки имеют отдельное время и UUID.

Firebase автоматически инициализируется стандартными Android resources из `android/app/src/main/res/values/firebase.xml`, в том числе при холодном фоновом запуске. В APK находятся только публичные настройки. JSON сервисного аккаунта хранится отдельно и после согласованного развёртывания поступает в Supabase Vault; в приложение не включается.

### Переход с debug на release

Release начиная с 1.1.0+6 использует постоянный сертификат `35a0b93b5286dca9a738c56a1084ea46be75c7da8d9aac8eba80c557b7bb0f77`. Он отличается от debug-сертификата. Android не разрешает поставить этот release поверх debug с тем же package name.

Если debug установлен: сначала убедиться, что правки появились в вебе, выполнить «Export backup» и проверить JSON. Затем удалить debug, установить release и войти в тот же аккаунт. Заметки аккаунта скачаются из Supabase; несинхронизированные локальные записи можно восстановить из экспорта. Не удалять приложение, пока локальные изменения не сохранены.

Если debug ещё не установлен, сразу использовать release. Последующие release APK подписываются тем же ключом и устанавливаются поверх предыдущего release с сохранением SQLite; номер сборки повышается при каждом обновлении.

### Проверки протокола

- `node --experimental-strip-types --test apps/web/tests/*.test.mjs` — порядок правок, повторная доставка, удаление, часы, два клиента RxDB с разным порядком офлайн-изменений и получение нескольких страниц. Команду выполнять из корня репозитория после установки зависимостей.
- `python3 apps/android/tools/test_schema.py` — SQLite и Android platform wiring.
- `cd apps/android/android && ./gradlew connectedDebugAndroidTest` — реальная миграция SQLite v1/v2→v3, ACK после новой правки, откат страницы, смена аккаунта и напоминания.
- `supabase/tests/before-migration.sql`, `supabase/sync-v2.sql`, `supabase/tests/after-migration.sql`, `supabase/tests/sync-v2.sql` выполняются последовательно в одной тестовой транзакции с `ROLLBACK`. Они не предназначены для применения как миграции в production.
