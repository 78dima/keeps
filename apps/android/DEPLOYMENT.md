## Использованная подготовка

1. Зафиксировать текущие версии и создать закрытые резервные копии: исходники/Compose/`.env`, текущую Edge Function `send-reminders` v12 и её настройки JWT. Для данных Supabase использована резервная копия, уже сделанная владельцем. Проверить читаемость резервных копий и возможность восстановления. Не сохранять секреты в Git или вывод инструмента.
2. Сохранить существующий Docker image под отдельным rollback-тегом. Проверить свободное место: при осмотре было около 3 GB. Не удалять прежний образ и не запускать тяжёлую npm/Next-компиляцию на VPS.
3. Скачать артефакт `monokeep-web-bundle` из успешного запуска в [VALIDATION.md](VALIDATION.md), сверить SHA-256, распаковать в отдельный release-каталог. Dockerfile в пакете копирует уже скомпилированный сайт в runtime-образ. Собрать новый image под отдельным тегом и проверить `/login` и `/sw.js` через временный localhost-порт. Не менять рабочий порт до завершения проверки.
4. Перед сменой версии сохранить/экспортировать важные офлайн-черновики в открытых браузерах. После обновления перезагрузить старые вкладки. Старая версия сайта не проставляла надёжное время текстовой правки: такие локальные снимки сохраняются отдельно, а не принимаются за гарантированно более новые.

## Порядок переключения

1. Применить `supabase/sync-v2.sql` как одну транзакционную миграцию. Проверки до/после сравнивают исходные даты и количество записей. Новые поля не удаляют заметки. Старые прямые записи без версии отклоняются, поэтому веб переключается сразу после миграции.
2. Развернуть подготовленный `send-reminders` с сохранением `verify_jwt=true`, существующих Telegram/VAPID secrets и расписания. Его подтверждения доставки больше не меняют время пользовательской правки; проверяется актуальная версия напоминания.
3. Переключить только сервис `web` на новый runtime-image через Compose override и `--no-build --no-deps`. Не запускать старый сервис API, не менять публичный адрес и переменные окружения. Сохранить прежний Compose и rollback-тег.
4. Через защищённый канал положить JSON сервисного аккаунта в Supabase Vault под именем `monokeep_firebase_service_account`, секрет диспетчера — `monokeep_sync_dispatch_secret`. Исходные локальные файлы находятся в игнорируемом `.secrets/`, с правами 0600; их содержимое не включается в APK/веб/Git.
5. Развернуть `sync-dispatch` с собственной проверкой заголовка `X-Sync-Secret` и `verify_jwt=false`, затем применить `supabase/sync-fcm.sql`. Доступ к выдаче конфигурации имеет только service_role. Cron проверяет очередь раз в минуту; текст заметок в FCM не передаётся.
6. Проверить сайт, Supabase advisors/логи, запуск cron и отсутствие ошибок отправителя. Установить проверенный APK с тем же аккаунтом и выполнить проверки ниже.

## Приёмка после обновления

- Правка в браузере появляется в открытом APK; правка в APK — в браузере.
- APK без сети: правка A, затем более поздняя веб-правка B. После подключения остаётся B. Повторить с более поздней правкой A; остаётся A. Сравнивается вся заметка, включая закрепление, теги и цвет.
- Удаление и восстановление, повторная отправка, выход/вход и смена аккаунта не теряют очередь и не показывают чужие данные.
- Старые локальные данные браузера мигрируют в `monokeepdb_v5`; точный снимок доступен в меню «Копия заметок до обновления». Старая неотправленная запись не блокирует новые заметки.
- Проверить FCM до закрытого приложения, WorkManager после возврата сети, открытие по локальному уведомлению, повторное включение напоминания, перезагрузку и Doze. Реальная доставка FCM на телефон пока не проверена; на CI проверено получение токена, серверные OAuth/validate-only и запуск диспетчера проверены отдельно.
- Сверить интерфейс и обновление уже установленного APK с сохранением базы. При несовместимой подписи сначала экспортировать старые локальные заметки; не удалять приложение без копии.

## Откат

Возврата только Docker image недостаточно: старый веб пишет по прежнему протоколу. Сначала сохранить изменения, появившиеся после выпуска, и остановить FCM cron. Затем в транзакции отключить новый протокол следующими командами; они проверены в тестовой транзакции с `ROLLBACK` на текущем проекте:

```sql
select cron.unschedule(jobid) from cron.job where jobname='monokeep-sync-fcm';
drop trigger if exists monokeep_signal_notes on public.notes;
drop trigger if exists monokeep_signal_tags on public.tags;
drop trigger if exists monokeep_version_notes on public.notes;
drop trigger if exists monokeep_version_tags on public.tags;
revoke execute on function public.sync_push(text,jsonb) from public,anon,authenticated;
revoke execute on function public.sync_pull(text,bigint,integer) from public,anon,authenticated;
revoke execute on function public.sync_clock() from public,anon,authenticated;
drop trigger if exists update_tags_updated_at on public.tags;
create trigger update_tags_updated_at before update on public.tags
  for each row execute function public.update_updated_at_column();
```

На проверенном production у `notes` не было пользовательского триггера обновления времени; у `tags` был только восстановленный выше `update_tags_updated_at`. Если состояние перед выпуском изменилось, использовать определения из свежей резервной копии.

Вернуть сохранённую Edge Function `send-reminders` v12 и прежний Docker image/Compose. Дополнительные SQL-поля, таблицы конфликтов и очереди оставить для восстановления, не удалять пользовательские данные. Новый APK временно получает ошибку RPC и сохраняет офлайн-очередь. Для повторного включения новой версии понадобится отдельная миграция повторного запуска с полной пересинхронизацией; исходный `sync-v2.sql` нельзя повторно применять вслепую поверх оставшихся объектов.
